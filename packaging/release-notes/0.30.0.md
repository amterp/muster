## Fixed

- **A stray ssh master on Muster's control path no longer holds a machine's panes unreachable.**
  After Muster's own ssh master died, another master could take over its control path without
  the forward to the machine's daemon. It answered `ssh -O check`, so Muster read the tunnel as
  up and never reopened it, and every pane on that machine stayed `unreachable`. Once its ssh
  has exited, Muster now also tries the forwarded socket. If nothing listens there, it ends
  whatever holds the control path and reopens the tunnel.
- **Reopen Closed Pane brings a Claude Code session back when its startup report was missed.**
  Only Claude Code's `SessionStart` hook told Muster the session's id, so a pane whose report
  never arrived reopened as a plain shell. The `Stop` hook now sends the id at the end of each
  turn. A startup report that fails also leaves its error in Claude Code's debug log
  (`claude --debug`) instead of being discarded. Sessions take this up when restarted.
- **Scrolling over an idle agent no longer makes it read `stuck`.** Wheel and click reports the
  agent had not read yet counted as unread input, so a Codex pane at an idle prompt could read
  `stuck`, and a stuck pane drops clicks. Only keys, pastes and doorbell rings count now. On
  Linux, about 4 KiB of pointer reports queued behind unread keys can hide those keys, so a
  program that really hangs there is read `stuck` only after the next key (`muster docs limits`).
- **A script that outlives its pane no longer posts as you.** `muster msg post` run with a
  closed pane's `$MUSTER_PANE` was recorded as coming from `@human`. It is now refused, and so
  is a `msg read` that would have marked your messages read. `muster msg --as NAME` still posts
  as NAME from there, and `join --name` still joins.
- **Codex's "Approaching rate limits" selector reads `blocked`.** A pane at that selector read
  `waiting` or `idle`, and a message for it was described as held behind a draft. The pane now
  reads `blocked` even when it has declared a wait, and `muster msg post` and `muster msg who`
  say the message waits on a dialog. The screen was rebuilt from a report and Codex's own tests,
  not recorded from a live selector.
- **`muster pane send --key` returns once the pane has redrawn.** A key sent to a dialog
  returned before the dialog moved, so the next key or `muster pane read` acted on the old
  screen: three Downs in a row could move the selection once. After its last key, a send with
  keys now waits until the pane's text has changed and been still for 100 ms, or 300 ms when
  nothing changes, and about a second at most while the pane keeps printing. It cannot tell
  which key a change answers, so send one key per command when each must land before the next.
  Sends of text alone are as fast as before. The same holds for the API's send.

Changes to the test suites and the build that do not reach an installed Muster are not listed.
