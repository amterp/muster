# who macOS charges for a pane's program after a daemon hands its panes over
#
# recorded 2026-09-28T09:15Z on macOS 26.4.1 arm64
# read in docs/observations/macos-26.4.1.md section 9
#
# A bundle built by `./dev --bundle` from this checkout, launched into a scratch
# HOME. Its app started the daemon through Launch Services (pid 76909, route
# launch_services), as a shipped Muster does. Its one pane then ran the probes
# below. Then `muster-daemon replace` handed every pane to a successor that the
# old daemon spawned (pid 79385), which is the same daemon-side path a handoff
# the app asks for takes. The old daemon exited. The pane that lived through the
# handoff ran the probes again, and so did a pane the successor made.
#
# Two sources, recorded side by side because they disagree:
#
# - `who`, a process asking responsibility_get_pid_responsible_for_pid about
#   itself (the only query that answers truthfully, section 7);
# - tccd's own AUTHREQ lines from `log show`, which name the identity it charges
#   and the subject it judges against.
#
# The protected reads are of Full Disk Access folders, which are denied without a
# prompt. Nothing here could put a prompt on screen, and none appeared.
#
# Not recorded: tccd's lines for the Full Disk Access reads after the handoff.
# They were denied without tccd being asked again, so what they were charged to
# is not in its log. The requests that did reach tccd after the handoff are
# Developer Tool checks that syspolicyd makes when a new unsigned binary runs,
# made for the `peek*` binaries as each pane started them. <scratch> stands for
# the directory they were built in.
